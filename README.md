# Demo

This project is a demo on how to use Loopress

## Features demoed

Every CI run (`test` and `deploy` jobs, GitHub and GitLab alike) boots a real, disposable
WordPress instance via `loopress/setup-ci` and pushes this repo's content to it with the real
`lps` CLI, in this order:

| Command | Source in this repo | Notes |
|---|---|---|
| `lps plugin push` | `loopress.json` `plugins` | Installs/activates `wpforms-lite` so `form push` below has something to write to. `plugin-check` demonstrates a plain WordPress.org plugin under Loopress management. |
| `lps snippet push` | `snippets/` | PHP/CSS/JS/HTML/text snippets, WPCode-backed on this instance. |
| `lps api push` | `api/`, `lib/` | Custom REST routes: a plain `GET` with the default `manage_options` permission (`hello.php`), a public `permission()` override with CORS `headers()` for a headless caller (`newsletter-signup.php`), one (`prices-in-currency.php`) enriching the `price` ACF field from `acf/field-groups/group_demo_pricing.json` with a live rate from an external currency API through `guzzlehttp/guzzle`. `webhook.php` uses `#[Permission]` for per-verb authorization (a public health-check `get()`, a signed `post()`). `orders/[order_id]/items/[item_id].php` combines two dynamic segments with a `#[Permission]` callback shared from `lib/ApiKeyGuard.php`. `WITH_MAJ_ENDPOINT.php` is deliberately invalid (uppercase filename), meant to demonstrate the client-side filename check rejecting it before any network call. No page in this demo actually sets a price, so `prices-in-currency.php`'s response is well-formed but empty, the point is the external call, not seeded content. |
| `lps acf push` | `acf/` | A field group, a post type, and a taxonomy. Options pages aren't included: they require ACF PRO, and this CI instance only has ACF free. |
| `lps composer push` | `composer.json` | Installs `hello-dolly` from wpackagist (a WordPress plugin, visible under `wp-content/plugins/` afterward) and `guzzlehttp/guzzle` (`use`d by `api/prices-in-currency.php`). |
| `lps form push` | `forms/` | A WPForms contact form. |

Several recipes are self-contained projects instead, each with its own `loopress.json` and
`composer.json`, pushed from their own directory (`cd <project> && lps ... push`) rather than
the site-wide config above (see `obsidian/Product/Cookbook Content Pipeline.md` for why):

| Project | Command | Notes |
|---|---|---|
| `post-to-pdf-dompdf-wordpress-rest-api/` | `lps composer push && lps api push` | `api/post-pdf/[post_id].php` shows a dynamic path segment rendering any published post as a downloadable PDF with `dompdf/dompdf` (fed the post's own `the_content`-filtered HTML), raw binary output instead of the usual JSON, mirroring the [post-to-PDF cookbook recipe](https://docs.loopress.dev/cookbook/documents-and-files/post-to-pdf-dompdf-wordpress-rest-api/) line for line. Post 1 ("Hello world!", WordPress's own default) is real seeded content, no stand-in needed. |
| `spreadsheet-export-phpspreadsheet-wordpress-rest-api/` | `lps composer push && lps api push` | `api/orders-export.php` turns completed WooCommerce orders into a downloadable `.xlsx`, behind an explicit `manage_options` `permission()`, with `phpoffice/phpspreadsheet`, mirroring the [spreadsheet-export cookbook recipe](https://docs.loopress.dev/cookbook/documents-and-files/spreadsheet-export-phpspreadsheet-wordpress-rest-api/). `composer.json` requires `wpackagist-plugin/woocommerce` alongside the PHP library, composer.json isn't just for pure-PHP dependencies. Composer installs WooCommerce's files but doesn't activate it, and `lps plugin push` refuses to run at all once a project has its own `composer.json` (it's authoritative for plugins there, no CLI command activates a wpackagist-installed plugin today), so activate WooCommerce in wp-admin (Plugins > Activate) same as any other WordPress plugin; CI does the REST-API equivalent (see `.github/workflows/loopress-ci.yml`). No order exists in a fresh install, so the exported file is well-formed but empty beyond its header row. |
| `instant-search-algolia-woocommerce-hooks/` | `lps composer push && lps hook push` | Two hooks instead of a route, mirroring the [instant-search-algolia cookbook recipe](https://docs.loopress.dev/cookbook/search-and-data-services/instant-search-algolia-woocommerce-hooks/): `hooks/algolia-index.php` keeps an Algolia `products` index current on `woocommerce_new_product`/`woocommerce_update_product` with `algolia/algoliasearch-client-php`, `hooks/replace-header-search.php` swaps WooCommerce's native search box for the recipe's React app via the `get_product_search_form` filter. `composer.json` requires `wpackagist-plugin/woocommerce` the same way as the spreadsheet-export recipe above, same WooCommerce-activation dance in CI. No product save happens in CI, so the hooks are deployed but never actually triggered, no Algolia credentials needed here; the recipe's `apps/algolia-search` React app isn't part of this repo, it has its own npm/vite build the site-wide config here doesn't host. |
| `image-resizing-intervention-image-wordpress-rest-api/` | `lps composer push && lps api push`, then `npm --prefix apps/image-shapes ci && npm --prefix apps/image-shapes run build && lps app push` | `api/image/[attachment_id].php` resizes and re-encodes a media library image to whatever width/height a caller asks for with `intervention/image`, returning a `data:image/webp;base64,...` URI, mirroring the [image-resizing cookbook recipe](https://docs.loopress.dev/cookbook/documents-and-files/image-resizing-intervention-image-wordpress-rest-api/). No dependency on any other plugin (pure PHP image library over GD), no WooCommerce-style activation dance needed. `width`/`height` are clamped to 2000 because the route is public. `apps/image-shapes/` is a small React app (`[loopress_app name="image-shapes"]` on a page, `?image=<attachment id>`) that fetches the same attachment as a banner, a card and an avatar, plus any width/height typed into its form. No attachment exists in a fresh CI install, so the route is deployed but never actually called there; `attachment_id=0` would 404 the same way a real missing id does. |
| `graphql-wordpress-rest-api-route/` | `lps composer push && lps acf push && lps hook push && lps api push` | `api/graphql.php` answers GraphQL queries against a `Post` type with `webonyx/graphql-php`, mirroring the [GraphQL cookbook recipe](https://docs.loopress.dev/cookbook/search-and-data-services/graphql-wordpress-rest-api-route/). `api/graphiql.php` is a second, bonus route: the interactive GraphiQL client (React + GraphiQL as ES modules from esm.sh, no build step) pointed at the route above, its default query targeting whatever the most recently published post happens to be. Unlike the article's generic `product` example, this project deliberately queries WordPress's own `post` type, no custom post type, no WooCommerce: `acf/field-groups/group_post_fields.json` attaches `reading_time`/`summary` to ordinary posts, so `lps acf push` runs before `lps api push`, and the route's resolver reads both fields with `get_field()`, not `get_post_meta()`, showing an ACF-defined schema and a custom API route composing in one project instead of two disconnected recipes. `hooks/post-meta.php` registers `reading_time`/`summary` as core REST-writable postmeta (`register_post_meta`) so a real client can write those same ACF-backed fields over `wp-json/wp/v2/posts`, not just read them through GraphQL; ACF's own "Show in REST API" field setting doesn't wire that up by itself on every ACF version. WordPress's own seeded "Hello world!" post (id 1) is real content here, no separate seed needed, same reasoning as post-to-pdf above. |
| `qr-code-generation-wordpress-rest-api/` | `lps composer push && lps cpt push && lps meta push && lps api push`, then `npm --prefix apps/ticket ci && npm --prefix apps/ticket run build && lps app push` | `api/ticket-qr/[ticket_id].php` renders a scannable QR code for one event ticket with `endroid/qr-code`, encoding the ticket's `home_url('/verify-ticket/')` link, mirroring the [QR code cookbook recipe](https://docs.loopress.dev/cookbook/documents-and-files/qr-code-generation-wordpress-rest-api/). `permission()` lets only a site admin or the ticket's own buyer (`_customer_id` postmeta) request it. `cpt/ticket.json` declares the `ticket` post type the route looks tickets up in and `meta/ticket.json` its `_customer_id` field, so `lps cpt push` and `lps meta push` run before `lps api push`. `composer.json` pins `endroid/qr-code` to `6.0.9` (6.1 needs PHP 8.4, 6.0.x runs on 8.2+ with the same `Builder` API). `apps/ticket/` is a small React app (`[loopress_app name="ticket"]` on a "My ticket" page) that fetches the route with the shortcode's `restNonce` and shows the logged-in buyer their ticket's QR code, or the route's own error message when `permission()` refuses. No ticket exists in a fresh install, so the route answers 404 until one is created. |
| `html-sanitization-htmlpurifier-wordpress-rest-api/` | `lps composer push && lps api push` | `api/import-article.php` cleans HTML pushed in by an external system with `ezyang/htmlpurifier` (an allowlist of tags, empty elements removed) before storing it as a draft post, mirroring the [HTML sanitization cookbook recipe](https://docs.loopress.dev/cookbook/content-and-data/html-sanitization-htmlpurifier-wordpress-rest-api/). `permission()` checks a shared secret from the `import_api_secret` option against the `x-import-secret` header with `hash_equals()`, so set that option before calling the route. `partner-article.json` is the external system's request body, the cookbook's own payload (an `onclick` and a `<script>` the route strips): `curl ... -H "Content-Type: application/json" -d @partner-article.json`. |
| `headless-sitemap-generation-wordpress-rest-api/` | `lps composer push && lps api push` | `api/sitemap-data.php` builds the sitemap of a headless front end's own domain with `icamys/php-sitemap-generator`: every published post and page as an absolute `<loc>` under the `headless_frontend_url` option (capped at 50,000 URLs, one file), mirroring the [headless sitemap cookbook recipe](https://docs.loopress.dev/cookbook/content-and-data/headless-sitemap-generation-wordpress-rest-api/). `permission()` checks the `sitemap_build_secret` option against the `x-build-secret` header with `hash_equals()`, and refuses when the option is empty (`hash_equals('', '')` is true). A fresh install lacks both options: `wp option update headless_frontend_url https://www.example.com` and `wp option update sitemap_build_secret <secret>`, plus pretty permalinks (`wp rewrite structure '/%postname%/'`) so the paths look like a front end's. The route answers 500 `no_frontend_url` until the first is set. `tests/e2e/headless-sitemap-generation-wordpress-rest-api.spec.ts` seeds a post, a draft and a page over REST, checks the XML is well-formed, in the sitemap namespace, absolute and on the front end's domain, and that a missing or wrong secret is refused; it skips itself when the recipe is not deployed or the options are unset (`SITEMAP_BUILD_SECRET` and `SITEMAP_FRONTEND_URL` override its defaults). |
| `headless-draft-preview-php-jwt-wordpress-rest-api/` | `lps composer push && lps api push` | `api/preview-link/[post_id].php` issues a 15 minute HS256 token for one post (`permission()`: `edit_post` on that post), `api/preview/[post_id].php` returns that post, draft or not, to a public caller holding a token for that exact post, with `firebase/php-jwt`, mirroring the [draft preview cookbook recipe](https://docs.loopress.dev/cookbook/auth-and-security/headless-draft-preview-php-jwt-wordpress-rest-api/). The signing key is never in the repo: define `PREVIEW_JWT_SECRET` in `wp-config.php` or set the `preview_jwt_secret` option (32 characters or more, e.g. `wp option update preview_jwt_secret "$(openssl rand -hex 32)"`). A fresh install lacks it, both routes answer 500 until it is set. `tests/e2e/headless-draft-preview-php-jwt-wordpress-rest-api.spec.ts` runs the whole loop when `PREVIEW_JWT_SECRET` is exported with the site's value, otherwise only checks the refusals. |
| `markdown-export-for-llms-html-to-markdown-wordpress-rest-api/` | `lps composer push && lps api push` | `api/markdown/[post_id].php` serves any published post as Markdown (`Content-Type: text/markdown`) with `league/html-to-markdown`, fed the post's own `the_content`-filtered HTML, mirroring the [Markdown export cookbook recipe](https://docs.loopress.dev/cookbook/content-and-data/markdown-export-for-llms-html-to-markdown-wordpress-rest-api/). The route is public on purpose (AI crawlers have no account); a draft, a private or password-protected post and an unknown id answer a JSON `404`. A fresh install has no post beyond "Hello world!" (id 1), so `curl <site>/wp-json/loopress-api/v1/markdown/1` is the quickest call. `tests/e2e/markdown-export-for-llms-html-to-markdown-wordpress-rest-api.spec.ts` creates its own posts, but is skipped until this project has been pushed, which `loopress-ci.yml` does not do yet. |
| `stripe-webhook-signature-verification-wordpress-rest-api/` | `lps composer push && lps api push` | `api/stripe-webhook.php` receives Stripe webhooks and verifies the `Stripe-Signature` header in `permission()` with `Webhook::constructEvent()` from `stripe/stripe-php`, then marks the order in the event's `metadata.order_id` as paid (`_payment_status` postmeta), mirroring the [Stripe webhook cookbook recipe](https://docs.loopress.dev/cookbook/auth-and-security/stripe-webhook-signature-verification-wordpress-rest-api/). No Stripe account needed: the spec signs its own payload with Stripe's scheme (`t=<timestamp>,v1=<HMAC-SHA256 of "t.payload">`). The secret is never in the repo: define `STRIPE_WEBHOOK_SECRET` in `wp-config.php` or set the `stripe_webhook_secret` option (`wp option update stripe_webhook_secret whsec_...`, the `whsec_...` value `stripe listen` prints with a real account). A fresh install lacks it, and the route refuses every request until it is set (an empty secret would let anyone sign a payload). A wrong signature, a modified body, a timestamp older than five minutes and a missing header all answer 401. `tests/e2e/stripe-webhook-signature-verification-wordpress-rest-api.spec.ts` runs when the route is pushed and `STRIPE_WEBHOOK_SECRET` is exported with the site's value, otherwise it skips itself. |

`seo/` is included as a **reference example only**, not pushed by CI: `setup-ci` activates both
RankMath and Yoast at once (on purpose, so the Loopress plugin's own test suite can exercise the
conflict), and `lps seo` correctly refuses to guess which one is authoritative when more than one
SEO plugin is active. A real site normally runs exactly one SEO plugin, and `lps seo push` there
works the same way as every other command above.

Not demoed here: `lps login` / `lps project push` / `lps project pull` / `lps snippet publish` -
these link a project to a Loopress account through an interactive browser OAuth flow, which
doesn't fit a headless CI run (see `e2e/README.md`'s "Why seeding, not real login" for the same
reasoning applied to the CLI's own end-to-end suite).

## E2E tests

`tests/e2e/` uses [`@wordpress/e2e-test-utils-playwright`](https://developer.wordpress.org/block-editor/reference-guides/packages/packages-e2e-test-utils-playwright/)
to check that the WordPress admin loads against a real instance. It runs in
`.github/workflows/e2e.yml` via `loopress/setup-ci`.

To run locally: boot WordPress with `loopress/setup-ci`, then set `WP_BASE_URL`, `WP_USERNAME`,
and `WP_PASSWORD` if your instance doesn't match the `loopress/setup-ci` defaults
(`http://localhost:8080`, `admin`/`admin`), then:

```bash
npm install
npm run test:e2e
```
